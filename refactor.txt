ROLE
You are performing a professional repository-wide refactor of a Roblox/Luau tycoon game.
This is not a mechanical cleanup pass. Read this entire specification before editing, inspect the relevant code before changing it, and preserve gameplay behavior unless this document explicitly identifies a bug or architectural migration.

PRIMARY OBJECTIVE
Bring the project toward a high-quality production architecture with:
- Clear ownership of mutable state.
- Explicit lifecycle and cleanup.
- Strong server authority.
- Compact, typed networking.
- Measurable performance improvements in Recv, Sent, CPU, and Memory.
- Idiomatic modern Luau.
- Minimal unnecessary abstraction.
- ECS only where ECS is actually a good fit.
- Completed migrations instead of old/new systems running in parallel.
- Dead code removed rather than modernized.
- Stable, testable domain boundaries.

GENERAL DECISION PRIORITY
When choosing between two implementations, prioritize:

1. NON-NEGOTIABLE ARCHITECTURAL RULES
======================================================================

1.1 Do not over-engineer.
Prefer the smallest implementation that provides correct ownership, lifecycle, typing, security, and performance.

1.2 Do not create abstractions that merely forward to Roblox/Luau APIs.
Examples of bad one-function wrappers:
- DestroyLater -> task.delay / Destroy
- FindChild -> FindFirstChild
- Tween -> TweenService:Create
- ClampNumber -> math.clamp

An abstraction is justified only when it owns meaningful policy, lifecycle, replacement/cancellation, typing, transactions, or domain behavior.

1.3 Do not convert everything to ECS.
Use ECS/Jecs for high-cardinality simulation/data-oriented workloads.
Do not force:
- UI
- Services
- Resource managers
- Network policy
- Singleton configuration
- Plain orchestration
into ECS without a real reason.

1.4 Do not store OOP/controller/service objects in ECS components just so systems can call methods on them.
Current examples of the anti-pattern include components carrying:
- Tycoon objects
- Controller objects
- Service objects
- callbacks/closures
- StateMachine/controller behavior

Target:
- Numeric entity IDs
- Typed plain-data components
- Behavior owned by systems
- Roblox Instance references only at explicit integration boundaries

1.5 Keep configuration immutable.
Do not mutate authored config tables to store runtime values such as current ammo, current state, current ownership, etc.

1.6 One mutable concern = one owner.
Avoid multiple systems writing:
- Humanoid.WalkSpeed
- Camera state
- Weapon ammo
- Profile/leaderstat UI values
- Session phase
- Environment shelter state

1.7 Finish migrations.
The codebase repeatedly has old + new systems active simultaneously. Remove displaced architecture after migration succeeds.

4. DATA / COMMERCE / PROFILE CORRECTNESS

4.1 ProductRewards / ProfileManager call style
A P0 mismatch was identified:
- ProfileManager functions are dot-style.
- ProductRewards had colon-style invocation in relevant paths.
This can shift arguments so the module table becomes the player argument and may still return PurchaseGranted even when the operation did not correctly apply.

Fix all reward handlers to call APIs using the correct call convention.
Do not acknowledge a purchase until the reward commit is known to be durable/successful.

4.2 Developer product receipt idempotency
CommerceService.ProcessReceipt needs a durable PurchaseId idempotency ledger.
DataTemplate did not contain a proper receipt-history structure.

Required behavior:
- Check PurchaseId against durable processed-receipt state.
- Apply reward transaction.
- Persist processed receipt / durable transaction state.
- Only then return PurchaseGranted.
- Make duplicate receipt delivery safe.
- Avoid granting twice across retries/server restarts.

4.3 PlayerRuntimeState shallow-copy bug
DefaultState contains nested GamepassOwnership = {}.
`table.clone(DefaultState)` only shallow clones, causing nested shared state between players.


This is not only a theoretical shallow-copy issue. It matches an observed multiplayer symptom:

- Player A joins and owns a gamepass / SWAT-related entitlement.
- PlayerRuntimeState for Player A writes ownership into GamepassOwnership.
- Player B joins afterward and does not own that gamepass.
- Because the nested GamepassOwnership table is shared by the shallow DefaultState clone, Player B can observe Player A's cached ownership.
- Commerce/GamepassCache may therefore treat Player B as already owning the item/pass, causing incorrect \"already owned\" behavior or granting/allowing gated interactions.

Gamepass ownership must be isolated per Player. Never share a mutable ownership map between player runtime states.

Required fix:
- Construct a fresh GamepassOwnership = {} for every newly created player state.
- Audit every other nested mutable field in default runtime/profile/session templates for the same shallow-clone problem.
- Keep GamepassCache keyed semantically by (Player, GamepassId), never by one shared ownership table.
- Refresh ownership from MarketplaceService when required, but do not let another player's cached value affect the result.
- Ensure PlayerRemoving clears all per-player ownership/cache state.

Required regression test:
1. Start a multiplayer server with at least two players.
2. Player A owns a tested gamepass.
3. Player B does not own it.
4. Join A first, allow GamepassCache:Warm(A) to complete.
5. Join B afterward and allow GamepassCache:Warm(B) to complete.
6. Assert GamepassCache:Has(A, PassId) == true.
7. Assert GamepassCache:Has(B, PassId) == false.
8. Verify Player B is prompted normally rather than being treated as \"already owned\".
9. Repeat with join order reversed and with player leave/rejoin.
10. Verify ownership remains isolated for SWAT, RainbowCarpet, Raygun, X2Cash, and any other registered pass.

Also review PromptGamepass:
- If the cache is not known yet, a fresh MarketplaceService ownership check may be required before deciding \"already owned\".
- Do not silently swallow Refresh failures and then treat an unknown cache state as authoritative.
- Prefer an explicit ownership cache state if useful: Unknown / Owned / NotOwned rather than conflating \"false\" with \"not loaded yet\".
Deep-create mutable nested structures per player.

4.4 PlayerRuntimeState ownership
Tycoon-scoped runtime state should not accidentally become whole-player-session state.
ResetTycoonState exists and resets Multiplier/Power/Armour/CanRebirth during tycoon cleanup.
However:
- ArmourEquipped can remain true across ordinary character death/respawn while the vest model is destroyed with the old character.

4.5 RarityBox economy boundary

4.6 Stat transport duplication

5. NETWORK ARCHITECTURE / BYTENETMAX
======================================================================

5.1 Canonical network layer
ReplicatedStorage/Network/Packets is the canonical first-party network contract.
Complete migration away from ACS_Engine.Events/legacy RemoteEvents where practical.

5.2 ByteNetMax version
Pinned package:
`elitriare/bytenet-max@0.2.5`

Important API facts from the bundled source:
- packet reliabilityType is `"reliable"` or `"unreliable"`
- default is reliable
- client packet `.send(data)`
- server packet `.sendTo(...)`, `.sendToList(...)`, `.sendToAll(...)`, `.sendToAllExcept(...)`
- `.listen(callback)`
- queries use `.invoke`
- `.listen(callback)` returns a cleanup/disconnect FUNCTION, not an RBXScriptConnection

Correct:
```luau
local Disconnect = Packet.listen(function(Data)
	...
end)

Disconnect()
```

Incorrect:
```luau
local Connection = Packet.listen(...)
Connection:Disconnect()
```

Audit all ByteNet listener cleanup accordingly.

5.3 Existing ByteNetMax transport limiter
ByteNetMax 0.2.5 already has transport-level inbound protection in the server processor:
- incoming data must be a buffer
- max buffer size
- token bucket based on bytes
- default MAX_BUFFER_SIZE is ~4096
- byte refill budget approximately 4 KB/s unless configured otherwise

Do not incorrectly state that ByteNet has no rate limiter.

However this is not enough:
one accepted buffer can contain many tiny logical messages.

5.4 Add first-party NetworkGuard
Do not fork/edit ByteNetMax for project-specific action thresholds.

Add a first-party boundary such as:
`Server/Networking/NetworkGuard.luau`

Responsibilities:
- Per-player aggregate logical action budget
- Per-packet token bucket
- Burst allowance
- Semantic validation hooks
- Player/session validation
- Metrics for accepted/dropped requests
- Cleanup on PlayerRemoving
- Optional severity/telemetry escalation

Concept:
ByteNet transport protection -> NetworkGuard -> gameplay handler

Rate limiting is primarily resource protection and trust-boundary enforcement.
A threshold violation normally means:
- drop/reject
- increment telemetry
not automatic permanent ban.

5.5 Do not use a client-obtainable auth token as authority
Current ACS AcessId/AuthToken model is not meaningful authority because the client can obtain/use the token.
Remove this architecture.
Server should derive authority from:
- player identity
- equipped Tool/server state
- server-known weapon config
- validated action context
- validated target/context

5.6 Reliable vs unreliable
Keep reliable for important discrete transitions:
- equip/unequip
- inventory mutations
- purchase results
- profile/commerce state
- final nuke result
- committed state changes

Use unreliable for frequently replaced presentation state where packet loss is superseded by the next update:
- laser transforms
- high-rate aim orientation
- transient cosmetic positions
- intermediate score displays where final state is separately reliable

Do not mark everything unreliable blindly.

5.7 Minimize payloads
Do not send whole stable config tables per shot/event.
Current ACS examples needing redesign include:
- ServerBullet(origin, direction, weaponData, modifierTable)
- HitEffect including whole weaponData
- Damage huge positional payloads with client settings/modifiers/token
- Equip with broad authored config data

Server/client should already know stable configuration by weapon identity.
Packets should carry only compact changing intent/state.

5.8 Prefer relevance over sendToAll
`sendToAll()` is valid for rare genuinely global events.
Do not use it as the default.

Audit:
- NPCSpeech
- BuildAssemble
- combat presentation
- world effects
- other nearby-only events

Use spatial/relevance lists where frequency/traffic makes it worthwhile.

5.9 Do not manually add another buffer serialization layer on top of ByteNetMax without profiling.
ByteNetMax already serializes compactly with buffers.

Consider usage of the Bit32 library when trying to represent items with a single integer.

10. RBXOBSERVERS / INSTANCE LIFECYCLE
======================================================================

RbxObservers is a good fit for this project as the Roblox Instance lifecycle boundary.

Use it for dynamic:
- CollectionService tags
- character/Instance appearance/disappearance
- attributes where setup/cleanup should pair automatically
- acoustic/environment authored tags
- prompt/tag lifecycle
- ECS registration boundaries

Do not use it for:
- ordinary static one-time traversal
- profile/network state
- UI store state
- numeric ECS simulation
- every decorative object

The project already uses Janitor.
Do not add Trove just to pair with RbxObservers.
Use:
RbxObservers -> per-observed-instance Janitor -> cleanup return function

Example:
```luau
local StopObserving = Observers.observeTag("ElectricityParts", function(Instance)
	if not Instance:IsA("BasePart") then
		warn(`ElectricityParts tag applied to non-BasePart: {Instance:GetFullName()}`)
		return
	end

	local Janitor = Janitor.new()

	Janitor:Add(Instance.Touched:Connect(function(Hit)
		HandleElectricityTouch(Instance, Hit)
	end))

	return function()
		Janitor:Destroy()
	end
end, { workspace })
```

RbxObservers is particularly appropriate for:
- WindShake current manual GetTagged/GetInstanceAddedSignal/GetInstanceRemovedSignal logic
- ElectricityParts
- future AcousticZone/AcousticPortal/AcousticNode registration
- custom prompt lifecycle if tags are intentionally used
- Instance -> ECS registration boundaries

When using observeTag, runtime-check the Instance type. Do not assume a tag guarantees BasePart.

5.2 ByteNetMax version
Pinned package:

Important API facts from the bundled source:
- packet reliabilityType is `"reliable"` or `"unreliable"`
- default is reliable
- client packet `.send(data)`
- server packet `.sendTo(...)`, `.sendToList(...)`, `.sendToAll(...)`, `.sendToAllExcept(...)`
- `.listen(callback)`
- queries use `.invoke`
- `.listen(callback)` returns a cleanup/disconnect FUNCTION, not an RBXScriptConnection

Correct:
```luau
local Disconnect = Packet.listen(function(Data)
	...
end)

Disconnect()
```

Incorrect:
```luau
local Connection = Packet.listen(...)
Connection:Disconnect()
```

Audit all ByteNet listener cleanup accordingly.

5.3 Existing ByteNetMax transport limiter
ByteNetMax 0.2.5 already has transport-level inbound protection in the server processor:
- incoming data must be a buffer
- max buffer size
- token bucket based on bytes
- default MAX_BUFFER_SIZE is ~4096
- byte refill budget approximately 4 KB/s unless configured otherwise

Do not incorrectly state that ByteNet has no rate limiter.

However this is not enough:

```luau
local StopObserving = Observers.observeTag("ElectricityParts", function(Instance)

		Janitor:Destroy()
	end
end, { workspace })
```

16. ENVIRONMENT / RAIN

Known RainModule problems:
- Main camera cover ray is slanted opposite rain direction rather than a stable shelter query.
- `inside` initializes true and is never set false.
- Random ±100 stud splash samples cast from high above camera.
- If a roof is hit, an emitter is deliberately positioned about 50 studs above the roof.
- Occluded rain speed ~70–100 and lifetime ~0.8 sec => travel ~56–80 studs.
- Therefore particles can cross a roof and visibly continue into sheltered space.
- Straight rain visual length further worsens clipping.
- If no hit while “inside”, fallback can emit at random heights around/above camera inside the building.
- Larger roofs increase the number of random roof-hit columns, which can create more penetrating above-roof emitters.
- High roofs/upstairs worsen the slanted cover-ray miss due to horizontal drift.
- SetCeiling exists but no callers were found.
- SetCollisionMode exists but no callers were found.
- old FindPartOnRay APIs remain.
- particle emitters do not collide with geometry.

Do not “fix” this by tuning 50, ±100, or lifetime alone.

Target precipitation renderer:
- small camera-local rain grid/tiles, e.g. ~3x3 initially
- per-cell raycast along actual rain path
- obstruction distance determines visible rain segment
- particle lifetime/position must never allow rendered particles to cross from exposed side through a blocking roof into sheltered side
- include safety margin for particle visual length/spread
- valid outside/window cells can still rain while roof-covered cells are clipped
- use hit surface for splash, not “hit roof then emit above roof”
- reusable RaycastParams
- intentional collision/tag policy
- audit CanQuery on permanent shelter geometry
- update occlusion at a modest rate such as ~10–20 Hz or based on meaningful camera/weather changes, then interpolate/fade presentation
- profile final frequency
- support CurrentCamera replacement
- remove obsolete ceiling/collision APIs if no longer meaningful

Testing:
- open sky
- low roof
- high roof
- huge roof
- roof edge
- upstairs floor/ceiling
- awning
- window/open doorway
- sloped roof
- moving in/out of shelter
- oblique wind rain
- transparent/decorative geometry
- CanQuery=false cases
- respawn/camera replacement
- different FPS

Add a debug visualization mode for sample cells/rays/hit state/exposure.

======================================================================
24. PCALL / XPCALL POLICY
======================================================================

Do not remove pcall globally.

Good uses:
- DataStore calls
- HTTP
- Players:BanAsync / UnbanAsync
- Path:ComputeAsync
- Roblox async/user-thumbnail/friend APIs
- authored animation/module loading that can genuinely fail
- optional module boundaries
- top-level system isolation where failure is reported

Bad/questionable uses:
- wrapping ordinary internal functions solely so programming errors disappear
- bare pcall with ignored error on critical operations
- swallowing save/cache failures

Known examples to improve:
- CastController wraps HitMod.HitEffect in bare pcall and discards errors
- CrosshairController pcall around ordinary RuntimeSettings getter is likely unnecessary
- CommerceService cache refresh pcall lacks useful handling
- Settings save pcall can silently fail
- Preload Destroy pcall hides unexpected lifecycle errors

If intentional isolation is needed, prefer:
```luau
local Success, Error = xpcall(function()
	...
end, debug.traceback)

if not Success then
	warn(`Operation failed:\n{Error}`)
end
```

Never let critical errors vanish silently.

25. MODERN LUAU / CODE QUALITY DO RULES
======================================================================

- Use modern Luau generalized iteration by default:
```luau
for Key, Value in Table do
	...
end
```

- Keep `ipairs` only when its stop-at-first-nil sequence semantics are intentional.
- Use numeric loops when the index matters.
- Prefer `GuiButton.Activated` for normal cross-platform GUI activation.
- Use mouse-specific events only for actual hover/drag/pointer semantics.
- Use ContextActionService for mapped gameplay actions.
- Use UserInputService for raw/held/pointer input.
- Handle held-state releases even when gameProcessed is true if cleanup semantics require it.
- Prefer guard clauses over deep nesting.
- Keep functions at one conceptual level.
- Use --!strict for maintained first-party runtime code.
- Do not add strict to dead files just to satisfy style; delete them.
- Treat `any` as a boundary smell.
- Runtime-check Roblox Instance types to narrow types.
- Use explicit domain types.
- Prefer typed tagged unions/enums over arbitrary strings where practical.
- Cache stable references instead of repeated hierarchy searches in hot loops.
- Make startup/setup/equip transitions transactional.
- Make teardown idempotent.
- Use generation/session IDs for delayed work.
- Use current APIs:
  - Workspace:Raycast
  - Model:PivotTo
  - modern constraints when behavior is equivalent
- Write comments explaining why/invariants, not narrating syntax.
- Remove/gate debug logs.
- Preserve gameplay behavior during architecture changes unless fixing a known bug.
- Separate behavior changes from broad formatting when possible.

27. EXAMPLE — TRANSACTIONAL EQUIP
======================================================================

Bad:
```luau
Runtime.IsEquipped = true
Runtime.Tool = Tool

local Config = require(...)
if not Config then
	return
end

local Rig = CreateRig(...)
if not Rig then
	return
end
```

Preferred:
```luau
local function TryBuildEquipState(Tool: Tool): EquipState?
	local Config = ResolveWeaponConfig(Tool)
	if not Config then
		return nil
	end

	local Rig = CreateWeaponRig(Tool, Config)
	if not Rig then
		return nil
	end

	return {
		Tool = Tool,
		Config = Config,
		Rig = Rig,
	}
end

local NextState = TryBuildEquipState(Tool)
if not NextState then
	return false
end

CleanupCurrentEquip()
CommitEquipState(NextState)

return true
```
